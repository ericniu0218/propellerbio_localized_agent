# Meeting transcripts

Lets someone ask the assistant what was said or decided in a meeting, and get
an answer with the meeting, date, and timestamp cited.

Meetings arrive two ways. Zoom records some of them for us. The rest are
recorded here, from the Meetings tab — a microphone in a room, or the audio of
an online call somebody is already sitting in. Both end up in the same storage
in the same format, so retrieval does not know or care which is which.

## How the pieces connect

```
Zoom  ──webhook──▶  zoom-transcript-vault        (public internet, a relay;
                     (separate repo)              stores metadata only)
                          │
                          │ POST /transcripts  (signed)
                          ▼
              Datacenter transcript connector    ← the customer's own storage
                 (their infrastructure)
                     ▲    ▲
                     │    │ GET /transcripts?from=&to=  (signed, INTERNAL network)
                     │    │
                     │    └──── app/tools/meeting_transcripts.py   ← this repo
                     │
                     │ POST /transcripts  (signed, INTERNAL network)
                     │
              app/meetings/  ← this repo: record in the browser, transcribe here
```

The vault is a relay on the public internet. It captures transcripts from
Zoom and pushes them into the customer's datacenter, holding no transcript
content itself. This repo reads them back.

**This system never calls the vault.** It queries the datacenter connector
directly over the internal network. Asking the vault instead would mean this
air-gapped deployment making an outbound call to the public internet to answer
a question, which defeats the air gap. `assert_internal_endpoint` in
`app/tools/datacenter_client.py` refuses a `DATACENTER_BASE_URL` that points at
an obviously public host.

## Configuration

```
DATACENTER_BASE_URL=http://transcripts.internal:8080
DATACENTER_SIGNING_SECRET=<same secret the connector holds>
DATACENTER_TIMEOUT_S=30
```

With neither set, the tool stays registered and returns a clear "not
configured" result instead of failing — the same pattern as the other optional
integrations. Nothing else in the system changes.

## Signing

Every request is signed, matching the vault's scheme exactly:

```
HMAC-SHA256(secret, f"{timestamp_ms}.{METHOD}.{path_with_query}.{body}")
```

sent as `X-Vault-Timestamp` and `X-Vault-Signature: v1=<hex>`.

The method and path are inside the signed message so a signature for one date
range can't be replayed against another. Because the *literal* path string is
signed, `app/tools/datacenter_client.py` builds the query string itself and
sends that exact string — `%3A` and `:` produce different signatures, so any
library that re-encodes the URL would break every request.

`tests/test_meeting_transcripts.py` pins this with vectors generated by
running the vault's real TypeScript `hmacSha256Hex`. If those tests fail, the
two services have drifted and every signed request between them will 401.

## Running it locally

`contrib/datacenter_connector/` is a working reference implementation of the
connector, so you can run the whole path without the customer's infrastructure.
See its README.

## How retrieval works

The connector contract only supports retrieval by date range, but people ask
by topic. So the tool pulls the meetings in a window and ranks locally:
transcripts are parsed into speaker-attributed cues, grouped into short
overlapping windows of conversation, and scored by token overlap with the
question. Only the best windows are returned — a month of meetings is far
larger than any context budget.

Scoring is deterministic keyword overlap, the same placeholder
`rag_search.py` uses, and swaps for embeddings behind the same interface once
the RAG ingest pipeline exists.

When nothing matches, the tool returns how each meeting opened — usually where
the agenda is stated — and **says explicitly that this is not a match**, so the
agent doesn't present an unrelated meeting as an answer.

## Where the transcript parser lives

Turning WEBVTT into speaker-attributed cues is done by
`bedrock.meetings.transcript` from **bedrock-private-ai**, the employee terminal
client, which uses the same code for its own meeting notes. This repo does not
keep a copy, so a parsing fix is made once and reaches both products.

- `requirements.txt` pins it to one commit. To pick up a change, update that
  commit hash on purpose and run the tests. The tool uses `Cue`, `parse_vtt`
  and `speakers`, plus `Cue.timestamp` and `Cue.render()`.
- The repo is private. Installing needs GitHub access; CI reads it with the
  `BEDROCK_PRIVATE_AI_TOKEN` repository secret, a read-only token for that repo.
- The import is guarded. Without the package (the Docker image does not install
  it), the server starts normally and `meeting_transcripts` returns "the
  transcript reader from bedrock-private-ai is not installed" instead of
  results.

## Recording a meeting here (`app/meetings/`)

The Meetings tab has a Record button. It captures the device's microphone, the
audio of a browser tab, or both mixed together, uploads the audio, and turns it
into a meeting with notes.

Everything runs on this machine: `whisper.cpp` for speech, and whichever local
model the deployment already uses for the notes. No audio and no transcript
reaches a third party, which is the whole reason this is a recorder rather than
a meeting bot — every off-the-shelf bot relays the call through its own servers.

### One-time setup

```bash
brew install whisper-cpp ffmpeg
mkdir -p ~/.cache/whisper-models && cd ~/.cache/whisper-models
curl -LO https://huggingface.co/ggerganov/whisper.cpp/resolve/main/ggml-small.en.bin
curl -LO https://huggingface.co/ggml-org/whisper-vad/resolve/main/ggml-silero-v5.1.2.bin

# Speaker identification. Optional — without these a recording still
# transcribes and is reported as unattributed.
mkdir -p diarization && cd diarization
curl -LO https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2
tar xjf sherpa-onnx-pyannote-segmentation-3-0.tar.bz2
curl -LO https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-recongition-models/nemo_en_titanet_small.onnx
```

The embedding model's release tag is spelled `speaker-recongition-models`
upstream — that typo is in the URL and is not a mistake here.

The VAD model is in a *different* Hugging Face repo from the speech model, and
it is not optional: without it, timestamps on a track containing silence drift
by minutes and every citation points at the wrong line.

`GET /workspace/api/meetings/readiness` reports anything missing, and the
Record button refuses to start until it is clean — finding out afterwards means
the meeting is already gone.

### Configuration

| Variable | Default | Why you would change it |
|---|---|---|
| `MEETING_MODEL_DIR` | `~/.cache/whisper-models` | models kept elsewhere |
| `MEETING_SPEECH_MODEL` | `<dir>/ggml-small.en.bin` | a larger model for accuracy, smaller for speed |
| `MEETING_VAD_MODEL` | `<dir>/ggml-silero-v5.1.2.bin` | |
| `MEETING_WHISPER_THREADS` | cores − 2, capped at 10 | leave the box more headroom |
| `MEETING_VOCABULARY` | unset | **set this** — see below |
| `MEETING_SUMMARY_MODEL` | `llama3.1:8b` | the local model that writes the notes |
| `MEETING_SUMMARY_ENDPOINT` | `http://localhost:11434/v1` | vLLM/SGLang in production |
| `MEETING_RECORDING_DIR` | `data/recordings` | where audio is kept |
| `MEETING_SEGMENTATION_MODEL` | `<dir>/diarization/sherpa-onnx-pyannote-segmentation-3-0/model.onnx` | speaker segmentation |
| `MEETING_EMBEDDING_MODEL` | `<dir>/diarization/nemo_en_titanet_small.onnx` | speaker embedding |

**`MEETING_VOCABULARY` is the highest-value setting here.** Whisper spells
words it does not know phonetically: across test runs of the same audio it
wrote "CROS" and then "CRAS" for "KRAS", and "PREA" for "Priya". Set it to the
drug names, assay names, gene symbols and people's names this customer actually
says out loud:

```bash
MEETING_VOCABULARY="KRAS, EGFR, G12D, Priya, interim analysis, enrollment, protocol"
```

It is used twice. First as whisper's decoder hint, which is what gets most of
these right. Then `app/meetings/vocabulary.py` repairs near-misses that slipped
through, because the hint is a bias and not a guarantee — the same audio gave
"KRAS" on one run and "CRAS" on the next, and a transcript that says CRAS is
not merely untidy, it is unsearchable.

That repair is deliberately conservative, and catches less than it could:

- only single-word terms; a multi-word entry stays a decoder hint only;
- one edit for a short term, two for a long one. Two edits on a five-letter
  name also turns "Rain" into "Ravi", so "PREA" → "Priya" is *not* repaired;
- an inflection is never touched — with `cohort` set, "cohorts" stays;
- a lower-case ordinary word must be a very close miss, so "grass" never
  becomes "KRAS"; a token shaped like a name (capitals, or containing digits
  like `G12C`) gets a little more latitude, because the shape is evidence.

Every substitution is recorded and shown in the meeting's provenance line, so a
reader can see the transcript was edited and what it said before.

### What it costs

Measured on an 18-minute recording on an 18-core Mac: **0.30x real time**, so
an hour-long meeting is about 18 minutes of work after it ends. Transcription
is 63% of that, diarisation 13%, the notes 23%.

It was 1.03x — an hour for an hour — until the slicing was fixed. Whisper pads
every slice it is handed to its 30-second window, so a one-second slice costs
what a thirty-second one does. Cutting the audio at every turn boundary made
440 slices for 18 minutes, about 3.7 hours of encoder work; cutting only where
the *speaker changes* made 355 and took a fifth of the time, with identical
word error and speaker attribution. If you change the slicing, measure this.

Uploading returns a job id and the browser polls rather than waiting. Jobs live
in memory: a server restart mid-transcription loses the job but not the audio,
which stays under `MEETING_RECORDING_DIR` and can be re-submitted.

### Measuring a change

`scripts/eval/` builds a meeting from text-to-speech with known ground truth —
who said what, and when — and scores word error and speaker attribution against
it. Run it before and after touching the pipeline. Two warnings from building
it: voices from one TTS engine are far more alike than real people (two female
voices merged into one speaker until they were re-picked across accents), so
trust a real recording over the synthetic one for anything about diarisation.

### Speakers

Zoom's local recordings can write one audio file per participant, which is
where bedrock-private-ai's perfect speaker labels come from — every word in
Bob's file was said by Bob, by construction. A microphone in a room offers
nothing equivalent, so the voices are told apart from the audio itself
(`app/meetings/diarize.py`): a segmentation model finds the voice changes, an
embedding model turns each stretch into a vector, and the vectors are
clustered. All ONNX, all local.

**Say how many people are in the meeting.** The Record dialog asks, and it
matters more than it looks. Left to work the number out for itself the
clustering over-splits badly on real meeting audio — on a genuine three-person
call it found 46 speakers at the default setting and still 24 at the most
conservative one, because people talked over each other and a half-second of
two voices at once embeds like neither of them. Given the number it is
reliable. Without one, diarisation still runs and the meeting page says the
count was guessed.

Two details worth knowing before changing any of this:

- **Diarisation runs before transcription, not after.** The cue is the unit a
  speaker label attaches to, and whisper cuts on silence — so two people
  talking without a gap land in one cue, and labelling it afterwards can only
  pick a winner. On a real recording that produced a single nineteen-second cue
  holding both sides of *"What's your name?" / "My name's Luke."* The voice-change
  offsets are handed to the slicer (`transcribe_track(..., split_at_ms=...)`)
  so each cue holds one person to begin with.
- **Overlapping turns are resolved shortest-first.** The diariser reports
  simultaneous speech as overlapping turns. Resolving those longest-first
  deletes every interjection sitting inside a longer turn, which collapsed a
  two-person recording onto one speaker. See `flatten()`.

Labels are provisional. `POST /workspace/api/meetings/{id}/speakers` replaces
`Speaker 2` with a real name across the transcript, decisions, action items and
people list in one pass — the Meetings page has the form. An action item owned
by "Speaker 2" is no more use than one owned by nobody.

### Recording a room full of people

The Record dialog's "Several people in the room" box turns off the echo
cancellation and noise suppression a laptop applies by default. Both are tuned
for one person close to the microphone and treat a voice from across the room
as noise to remove — which is exactly the voice worth capturing. Automatic gain
stays on, to lift the quiet far-side speakers instead.

### Capturing an online meeting

Chrome only exposes audio through `getDisplayMedia` for a **tab**, and on macOS
whole-screen audio is not available at all. In practice:

- **Join the call in a browser tab** (Zoom, Meet and Teams all support this) and
  tick "Also share tab audio" in Chrome's picker. This is the path that works
  everywhere with no extra software.
- **Using a desktop app instead?** Install a loopback audio device (BlackHole,
  Loopback) and pick it as the microphone. It appears in the device list
  automatically.

## Known gaps

- **Zoom meetings carry no access groups.** Meetings recorded here do, and
  both sides enforce them; meetings arriving through zoom-transcript-vault do
  not, because that relay has not been taught to set them. They stay readable
  by everyone until it is. This is the one remaining half of access control.
- **Redaction is regex, not clinical NER.** It catches SSNs, MRNs, emails,
  phone numbers and dates of birth. It does **not** catch a patient's name said
  out loud, which is the likeliest identifier in a recorded meeting.
  `phi_redaction.py` exposes `ner_hook` for a real model; until one is
  deployed, a redacted transcript is not a clean one.
- **A voice print is not authentication.** It can be fooled by an
  impersonation and confused by a cold, and nothing proves the person who
  enrolled is who they said. It saves typing names; it must never gate access.
- **Semantic ranking is tuned to reject.** Static embeddings do not separate a
  true synonym match (0.179 measured) from an unrelated question (0.124)
  cleanly, so the threshold picks which error to make and picks the miss. A
  better model raises the ceiling; a lower number does not.
- **No retention policy.** Transcripts accumulate in the datacenter forever.
  Whoever owns that storage owns deciding how long meetings are kept. Recorded
  audio also accumulates under `MEETING_RECORDING_DIR` and nothing prunes it.
- **Recording consent is left to the person recording.** The UI shows a live
  indicator and warns before starting, but the product does not collect or
  record anyone's consent. Several US states require all parties to agree.
- **Recording jobs do not survive a restart.** They live in one process's
  memory. Moving this off a single box means a real queue.
- **No PHI redaction on recordings either.** The same gap as above, and a
  recording is the likeliest place for a patient to be discussed by name.
